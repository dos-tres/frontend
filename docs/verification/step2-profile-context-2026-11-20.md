## 결론

기본 정보와 맞춤 조건은 브라우저 localStorage에 보관한다. 현재 추천에 필요한 값만 명시적으로 JSON에 담아 서버로 보낸다. 이름·전화·이메일·생년월일 원문은 추천 API로 전송하지 않는다. 추천과 요약은 서버가 계산한다. **챗봇 API는 현재 backend에 없어 ‘AI가 로컬 정보를 받는다’는 흐름은 아직 구현/검증되지 않았다.**

| 로컬 입력 | 서버 전달 | 백엔드 사용 / UI 기준 |
|---|---|---|
| 이름·전화·이메일 | 없음 | 로컬 기본 정보. 추천과 무관 |
| 생년월일 | profile.age | 만 나이만 계산. DB 후보의 age_min/age_max 조건에 사용 |

| 현재 상태 | profile.job | 재직→회사원, 재학→학생, 쉬고 있어요→쉬는 중. 그 외 선택값은 서버 계약에 맞음. policy jobCd_nm 자격 비교 |

백엔드가 지원하는 sex/situations는 현재 FE 입력·전달에 없다. 추가 수집이 필요한지 별도 결정하며 값을 추측해 보내지 않는다. 서버가 job/school을 받더라도 상위 추천이 반드시 변하는 것은 아니다. 후보 건수는 나이·지역으로 조회한 **자격 후처리 전 건수**이므로 job/school 반영 여부를 후보 건수 변화만으로 판정하지 않는다.

## 백엔드 협의용 초안 (미전송)

현재 나이/지역/현재 상태/학교/관심 연결에는 필수 수정이 확인되지 않았다. 아래는 전체 목적 완성을 위한 **미구현 계약**이다.

- 챗봇 API: 어떤 endpoint와 요청/응답으로 기존 로컬 정보를 받는지 합의 필요. 필요한 조건과 사용자가 동의한 맥락만 전달하고, 이름/연락처를 통째로 LLM에 보내지 않는다. 저장된 값이 있는 항목은 다시 묻지 않고 변경 의사를 확인하는 규칙 필요.
- participation_preference/group_size: 온라인·방문 선호 및 모임 규모를 실제 추천에 쓰려면 요청 필드뿐 아니라 프로그램의 운영방식/규모 메타데이터와 추천·미확인 처리 규칙 필요. 지금 face_to_face는 대면 부담 응답이므로 대체 필드로 사용하지 않는다.
- 경험: experiences를 AI 상담 맥락으로 사용할지 합의. 자유문장 그대로 무조건 전달하지 않으며 추천에 필요한 목적·범위·미입력 처리부터 결정.
- 관심 우선순위: 현재 명시한 진단 관심이 프로필보다 우선한다. 이대로 유지할지 ‘가장 최근에 수정한 관심’으로 바꿀지는 제품 결정. 현재 규칙을 안내했고 임의로 서버 계산이나 과거 이력을 변경하지 않음.
